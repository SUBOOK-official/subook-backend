# 자동 합배송

2026-09-08: 관리자 주문·배송의 CJ 송장 출력에서 단건/일괄 선택 모두 자동 합배송한다.

- 배송준비(`preparing`, 레거시 `paid`)이면서 운송장이 없고 미환불 품목이 남은 주문이 대상이다.
- 동일 회원 ID + 수취인 + 전화번호 + 우편번호 + 기본주소 + 상세주소가 일치해야 한다.
  전화번호는 숫자로, 주소는 앞뒤/연속 공백만 정리한다. 상세주소의 숫자·기호는 보존한다.
- 비회원, 구매자 정보 누락, 미해결 환불 신청, 이미 발송된 주문은 새 합배송에서 제외한다.
- 한 주문만 선택해도 다른 페이지/필터의 동일 조건 주문을 미리보기에서 보여준다.
  표시한 그룹 전체를 한 요청으로 발급하며, 미리보기 이후 변경된 품목/배송지는 재확인한다.
- 원 주문번호·결제·배송비·환불·정산 단위는 유지한다. CJ에는 대표 주문번호, 전체 미환불 품목,
  `BOX_QTY=1`로 한 번 접수한다. 양쪽 주문에 같은 운송장을 원자적으로 기록한다.
- 묶인 어느 주문에서 재출력해도 전체 품목을 포함한 라벨을 돌려준다. 일괄 재출력도 운송장별 한 장이다.
- 배송 시작 알림은 출력 요청 내 운송장당 한 번. 배송조회 크론은 같은 운송장을 한 번 조회하고
  각 주문의 배송완료/자동확정 예정 시각을 처리하며, 실행 내 완료 알림도 운송장당 한 번 보낸다.

## 중복 발급 방지와 복구

`order_delivery_groups`와 `order_delivery_group_members`는 RLS 활성화, service_role 전용이다.
프론트는 관리자 인증을 검사하는 `api/admin/cj-delivery`만 호출한다.

1. DB에서 주문/품목을 잠그고 발송 그룹을 선점한다(`claimed`). 한 주문은 한 그룹에만 속한다.
2. 주소정제와 채번 후 CJ 예약 **전** 번호/분류코드를 기록한다(`booking`).
3. 예약 성공 시 같은 DB 트랜잭션에서 그룹 확정과 모든 주문의 `shipping` 전이를 수행한다.
4. 채번 전 실패는 해제하고 재시도한다. 죽은 `claimed` 작업은 10분 뒤 회수한다.
5. CJ가 명시적으로 신규 예약을 거부한 경우(`E`, 중복 복구 경로 제외)도 선점을 해제한다.
   CJ 예약의 통신 실패는 재전송하지 않고 번호를 보존한다. 중복 예약의 기존 취소/재접수 복구는 유지한다.

`booking` 상태가 남고 결과 확인 오류가 표시되면 해당 운송장과 CJ 예약을 운영자가 확인해야 한다.
실제 접수 성공이 확인되면 해당 그룹에 `admin_transition_order_delivery(id, claim_token, 'registered')`를
호출해 기존 번호를 확정할 수 있다. 확정 후 어드민에서 재출력한다. 접수가 없거나 취소 완료임이
확인된 경우에만 `'rejected'`로 해제한다. **확인 없이 강제 재발급/선점 해제하지 않는다.**
`claim_token`은 서버 작업 소유권 검사용이며 사용자 화면에 반환하지 않는다.

활성 선점 중에는 상태/배송지 변경과 품목 환불을 DB 트리거로 차단한다. 배송중 전이 후에는
기존 주문별 환불/정산 정책을 그대로 따른다. 새 개인정보 사본은 저장하지 않는다.

## 검증

- 프론트: `node --test apps/admin-web/tests/deliveryGroups.test.js` (frontend 저장소에서 실행).
- DB: `supabase/tests/combined_order_delivery.sql`은 `delivery_test_20260908` 전용 테스트 스키마용이다.
  최소 orders/order_items fixture와 migration의 스키마를 이 이름으로 치환한 뒤, 한 트랜잭션에서
  실행하고 rollback한다. 실제 public 주문 테이블에서 fixture를 실행하지 않는다.
- 실제 CJ 접수 대신 HTTP mock으로 예약 한 번, 품목 합산, 재출력, 응답 유실/재시도, 미리보기 변경을 검증했다.
- 테스트 주문 브라우저에서 2주문 → 1박스/1장과 라벨의 합배송 주문번호·총수량을 확인했다.
