# 구매자 환불 대상 교재 선택

2026-10-06 운영 요청: 답이 적혀 있다는 환불 사유만으로는 여러 교재 중 대상을 식별할 수 없었다. 구매자가 주문 교재·옵션을 보고 한 품목 이상 선택하도록 한다.

- `request_member_refund(bigint,text,bigint[])`는 주문 소유권과 기존 배송 상태·7일 창·1회 신청 조건을 유지한다. 타 주문 품목, 없는 품목, 기환불 품목, 빈 선택은 저장 전에 거부한다.
- `order_refund_request_items`에 품목 ID를 저장하고 동일 트랜잭션에서 주문 신청 시각·사유를 기록한다. 사유나 교재 제목으로 대상을 추측하지 않는다.
- RLS는 본인 주문 또는 관리자 조회만 허용한다. authenticated는 SELECT만 가능하고 접수는 RPC를 경유한다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 캐시된 구버전 2인자 RPC는 새로고침 안내를 반환한다. 기존 신청의 대상은 소급해서 채우지 않는다. 특히 ORD-2609-0373은 별도 고객 확인이 필요하다.
- 주문 단위 미해소 신청 조건은 그대로 유지한다. 대상 선택만으로 환불, 반품 접수, 정산 취소가 실행되지는 않는다.
- 구매자 구매내역은 선택한 품목에 접수 표시를 붙인다. 관리자 주문 상세·환불 화면에는 교재명·옵션·수량을 표시한다. 품목 조회 실패와 과거 미기록을 구분한다.

검증: PGlite에서 실제 migration/RPC 실행, 인증·RLS·다른 주문/기환불/중복/빈 선택·기존 자격 조건·신청 저장·정산 생성 보류 검증. 기존 반품/정산 회귀 테스트도 통과. Docker가 설치되지 않아 `supabase db reset` 대신 격리된 PostgreSQL 호환 런타임으로 검증했다. 프런트엔드는 lint, 두 앱 build, public 테스트 및 390px 모바일/데스크톱 브라우저 검증. 브라우저 검증은 실제 컴포넌트와 요청·조회 함수를 쓰되 데이터 전송은 테스트 클라이언트로 격리했다. 실제 주문 신청·환불은 실행하지 않았다.

배포: 해당 migration만 dry-run 후 적용, 두 웹앱 배포. 롤백 시 기존 2인자 함수 복원 후 앱을 되돌린다. 품목 테이블은 신청 이력 보존을 위해 유지한다.
